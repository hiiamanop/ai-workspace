# GenOffice Browser-Native `.docx` File I/O Design

## Goal

Make GenOffice's document editor (`/document`, running as a plain browser
page — no Electron) actually able to open an existing `.docx` from the
user's computer and save changes back to it, instead of the current
`desktop-stub.ts` stubs that silently no-op every open/save action and
always start a blank document on page load.

Bundled in the same effort: fix a real docx-engine bug where paragraph
formatting inherited from a Word style (not a direct per-paragraph
override) is invisible to code that reads `Block.format` — it renders
correctly on screen (CSS already resolves it) but is lost everywhere else
(toolbar state, AI tools, `.docx` export).

## Non-goals

- No server-side document storage, recent-files list, or crash-recovery —
  none of those have a backend to live in yet (`@genoffice/project-store`
  only tracks chat history, not document bytes; see
  `docs/superpowers/specs/2026-08-12-inline-citations-design.md`'s "Out of
  reach" precedent for the same reasoning). `getRecentFiles()` stays `[]`,
  `writeRecoveryCopy()` stays a no-op.
- No cloud deployment work — out of scope per explicit user decision, this
  project is still local-dev-only.
- No `.xlsx`/`.pptx` (Sheets/Slides) — docs only.
- No change to the real Electron build's file I/O (`docs-main.ts`) — this
  is additive, browser-only.

## 1. Architecture: everything stays client-side

`@genoffice/docx-engine` (`parseDocx`, `generate.ts`) has no Node/Electron
dependency — confirmed by reading it: it's plain browser-safe TypeScript,
already used renderer-side even in the real Electron app (the Electron
main process only moves raw bytes; it never parses OOXML). This means
open/parse/edit/generate/save can all happen **in the browser tab**, with
zero round-trip to this project's own server — `desktop-stub.ts` is the
only file that changes.

## 2. File access: File System Access API, with a universal fallback

Feature-detected via `'showOpenFilePicker' in window` (Chrome/Edge; not in
Firefox/Safari as of this writing).

**When available:**
- **Open**: `window.showOpenFilePicker({ types: [{ accept: { '...wordprocessingml.document': ['.docx'] } } ] })` → a `FileSystemFileHandle` → `getFile()` → `arrayBuffer()`.
- **Save** (document already has a handle from open/save-as/save-new): `handle.createWritable()`, write the generated bytes, close — no dialog, matches the "just hit save" feel of the real app.
- **Save As**: `window.showSaveFilePicker({ suggestedName, types: [...] })` → write → the new handle becomes the document's handle for future plain saves.

**Fallback (no File System Access API):**
- **Open**: a hidden `<input type="file" accept=".docx">`, triggered programmatically, read via `FileReader`/`arrayBuffer()`.
- **Save / Save As / Save New**: build a `Blob` from the generated bytes, create an object URL, trigger it via a hidden `<a download="name.docx" href="...">`, revoke the URL after. Every save in this path is effectively "download a new copy" — there is no way to write back to the original file without the File System Access API, and no dialog to ask the user where it goes (the browser's own download location applies). This is a real, user-visible UX gap on unsupported browsers, not hidden from the user (see Error Handling below).

**State:** the current document's `FileSystemFileHandle` (when available) lives as module-level state in `desktop-stub.ts`, mirroring the existing pattern for `webSearchCitationOffset` in GenOffice's `tools.ts` — one open document per browser tab, matching how the app already behaves (no multi-document-per-tab concept exists in the browser build).

## 3. Mapping to `DesktopApi`'s existing contract

`DesktopApi` (`genoffice/apps/docs/src/shared/ipc.ts`) already defines the
shape every caller expects — `desktop-stub.ts` needs to fulfill it
faithfully, not invent a new one:

- `OpenFileResult { path: string; name: string; data: ArrayBuffer; hash: string }` — `path` is used renderer-side purely as an opaque identifier (stored in doc state, shown in export-completion messages) and is **never** parsed as a real filesystem path anywhere in the renderer (confirmed — no `path.dirname()`/`path.join()`-style manipulation of it exists client-side). A synthetic value (the picked file's name, or a `webfile://<name>` scheme to make it visually distinguishable from a real path) is safe. `hash` — real app uses sha256 of the raw bytes for external-modification detection; browser version computes it the same way via `crypto.subtle.digest("SHA-256", data)` for API-shape consistency, even though there's no external-modification detection to power in this browser build (no background process could modify a file the browser doesn't have a live handle to anyway).
- `openDocx()`, `openDocxPath()` (ignored — no synthetic "path" is re-openable without a fresh picker; can return `null`), `consumePendingOpenDocx()` (no launch-time file association in a browser tab — stays `null`), `consumeNewBlankDoc()` (stays `true` — every fresh page load starts blank, matches current behavior, per Non-goals).
- `saveDocx(path, data, auto?)`, `saveDocxAs(defaultName, data)`, `saveDocxNew(defaultName, data)` — return `{ ok: boolean; path?: string; error?: string }` shaped exactly like the Electron versions; `path` in the response is the same synthetic identifier scheme as above.
- `onOpenDocx`/`onRenamedDocx`/`onTeardown` stay no-op subscriptions (return an unsubscribe no-op) — none of these events can originate from a browser tab.

## 4. Error handling

- File System Access API's picker being cancelled by the user throws a
  `DOMException` named `AbortError` — this must be caught and treated as
  "user cancelled," not surfaced as a failure (`{ok: false, error: ...}`
  would show a spurious error toast for a normal cancel).
- A `.docx` that fails to parse (corrupt file, or genuinely not a `.docx`
  despite the extension) must produce a clear, user-visible error — reuse
  whatever error path `file-actions.ts` already has for a failed
  `parseDocx()` call in the Electron build (there should already be one,
  since even native file opens can hit a malformed file).
- On the fallback path (no File System Access API), the UI must make it
  obvious that "Save" downloads a new file rather than overwriting the
  original — a first-time notice or persistent label change, decided
  during planning, not a silent behavior change from what Chrome/Edge
  users see.

## 5. docx-engine paragraph-format inheritance fix

`buildTextParagraph` (`genoffice/packages/docx-engine/src/parse.ts`) merges
exactly one style-inherited property into the paragraph's `format` object
today — `autoSpace`, via an explicit "if paragraph didn't set it and a
style is attached, pull it from the style's resolved `display`" block.
`styleDisplayOf()` already resolves every other paragraph-format property
the same way (through the `basedOn` style-inheritance chain) for on-screen
CSS rendering — which is why alignment *looks* right today even when it's
missing from `Block.format` — but `buildTextParagraph` never pulls those
other properties down into `format`, so any code reading `Block.format`
directly (the alignment toolbar's active-state check, AI tools inspecting
paragraph formatting, `.docx` export/`generate.ts`) sees them as absent.

**Fix:** mirror the existing `autoSpace` fallback block for the other
properties `styleDisplayOf()` resolves: `align`, indent variants,
`spaceBefore`/`spaceAfter`, `lineSpacing`, `keepNext`/`keepLines`,
`contextualSpacing`. Mechanical, low-risk — same merge pattern repeated
per property, not a redesign.

## Testing

- `desktop-stub.ts`'s new open/save logic: unit-testable by mocking
  `window.showOpenFilePicker`/`showSaveFilePicker` and the File System
  Access API's handle/writable interfaces (mockable plain objects — no
  real browser API needed for the test itself). Cover: happy-path
  open→edit→save (no dialog), save-as writing to a new handle, the
  cancel-is-not-an-error case, and the fallback path's Blob/object-URL
  construction (feature-detection forced off in the test).
- `buildTextParagraph`'s format-inheritance fix: extend
  `docx-engine`'s existing parse tests with a paragraph that sets no
  direct override for one of the newly-fixed properties but is attached to
  a style that does — assert `Block.format` reflects the style's value,
  for each of the properties being fixed.
- No end-to-end/manual-only gap expected here (unlike the citation-chip UI
  work) — the File System Access API mocks entirely in `jsdom`/Node, so
  this can have real automated coverage, not just manual verification.
  Manual verification is still worth doing once for the real
  Chrome/Edge-vs-fallback behavior split, but isn't the *only* net.

## Out of reach

- Recent files, crash-recovery, external-modification detection (no
  server storage to back any of these yet).
- True "save without re-picking" on Firefox/Safari (File System Access API
  limitation, not fixable from this codebase).
- Cloud deployment.
- **Deferred during final review (2026-08-12):** the paragraph-format
  inheritance fix (§5) makes style-derived values visible in `Block.format`,
  which means `mergePPrFormat` now sees those fields as "changed" the moment
  *any* property on that paragraph is directly edited and saved — so editing
  one property (e.g. alignment) on a paragraph whose other formatting comes
  purely from its style bakes that style's spacing/indent/line-spacing values
  in as direct per-paragraph overrides on save, silently detaching the
  paragraph from future style edits. Rendering is unaffected (identical
  output at save time); only future style-inheritance behavior changes.
  Root cause: `ParaFormat` has no way to distinguish "value came from the
  style" from "value is a direct override" — a real fix needs that
  distinction at the type level (e.g. a parallel per-field source map),
  which is a bigger change than was safe to make inside this plan's fix
  wave. Revisit as a dedicated follow-up if it causes a real user-facing
  complaint (a style edit not propagating to a paragraph the user never
  meant to detach).
